# QualityOps — Production Management Workflow (Phase 5)

## Purpose

Manage production batches from planning through active production to completion or cancellation. Capture batch quantities and downtime events so that later phases can connect inspections, defects, and analytics to traceable production records.

## Primary workflow

1. An authorized user selects an active product, production line, machine assigned to that line (where the schema models this relationship), and active shift.
2. The user creates a production batch with its unique batch code, production date, planned quantity, and initial status as allowed by the existing schema.
3. As production progresses, authorized users record actual produced quantity and quantity dispositions supported by the current schema: accepted, scrap, and rework pending.
4. Users can search, filter, open, and view batch details.
5. A batch may transition only through valid states defined by the existing schema/business rules. Completion must satisfy existing database reconciliation constraints.
6. Users can record equipment/line downtime with a reason, start time, and optional end time. Duration should be calculated consistently with the existing `downtime_records` schema rather than accepted as arbitrary user input when duration is generated by the database.
7. Significant changes are recorded in `audit_logs` through the existing audit service.

## Quantity semantics

Do not conflate inspection sample failures with whole-batch quantities. Phase 5 manages batch-level production quantities only. Inspection sample sizes and defect occurrences belong to their later dedicated phases.

At minimum, respect the actual constraints for:

- `planned_quantity`
- `produced_quantity`
- `accepted_quantity`
- `scrap_quantity`
- `rework_pending_quantity`

The established model includes constraints named `chk_batch_disposition_sum` and `chk_batch_completed_reconciled`. Inspect their exact definitions and make the service/UI agree with them. Do not weaken or replace correct constraints to make tests pass.

## Role/permission proposal

Confirm this proposal against the existing canonical role set and documented authorization policy before coding:

- `ADMIN`, `QUALITY_MANAGER`, `SUPERVISOR`, `INSPECTOR`, `OPERATOR`, `VIEWER` may read production records if authenticated.
- Production batch creation and in-progress quantity updates should be limited to `ADMIN`, `SUPERVISOR`, and `OPERATOR` according to the established policy.
- Completion, cancellation, or correction of completed records should require appropriate elevated permissions (at minimum `ADMIN` and `SUPERVISOR`) and must be audited.
- `VIEWER` is read-only.
- Never trust a frontend-only permission check; enforce permissions in the API.

## Out of scope for Phase 5

- Quality inspections and inspection results
- Defect records or Pareto calculations
- CAPA workflow
- Business analytics dashboards
- Notifications
- ML/AI predictions
- New authentication/session implementation

Those will be handled in later phases. Existing authentication, contracts, PostgreSQL constraints, and audit infrastructure must be reused.
